### Core ideas
- **Design doc = contract.** Decide the core loop, win/lose rules and scope first; everyone builds against the same document.
- **Content is data, not code.** Story nodes, choices, effects and jumps live in data files; the engine only reads data and applies rules.
- **Game = one state object + a state machine.** Each choice changes state → apply effects → check death → jump to the next node.
- **Logic and presentation apart.** Rules (`engine.js`) never touch the page; rendering and effects (`ui.js`) never decide rules.
- **Asset pipeline.** Art is generated by scripts and referenced by key through a manifest; missing assets fall back gracefully.
- **Saves = serialized state + version number,** so old saves can be migrated instead of breaking.
- **Tools pay for themselves.** A link checker plus Monte-Carlo playthroughs is how balance gets tuned.

### What worked
1. **Spec first.** Writing `docs/SPEC.md` before any agent started meant there were zero integration conflicts. It froze the node schema and the exact sprite and scene key list, so the writer could reference art that didn't exist yet.
2. **Ownership by folder.** Each role owned whole folders (`data/`, `assets/`, `src/`), and only the dev log was shared. Nobody overwrote anyone else's files.
3. **Data-driven, pure engine.** `engine.js` has no DOM, so the validator runs the real rules in Node. Simulating 3,000 runs per route found real problems that reading the text never would:
   - a death ending that was never reached
   - average run length below the target
   - a near-softlock
4. **Playable early.** Missing art was drawn as a pixel slime and missing files didn't break the boot, so the game was playable about 20 minutes in, long before content was finished.
5. **New requests as optional fields.** Each mid-run request became one optional field in the spec, and old data stayed valid with no rework:
   - lore text (`more`)
   - alternate names (`aliases`)
   - cause of death (`ending.cause`)
   - places in the codex (`cat:"place"`)
6. **IP rules decided up front.** Named canon characters only appear as `omen_*` scene images, with no portraits and no logos. Because this was decided at the start, it never had to be argued later.
7. **Screenshots read as images.** Reviewing screenshots and contact sheets caught real problems that tests pass over:
   - overlapping toasts
   - dark sprites disappearing on dark scenes
   - truncated text

### What hurt
1. **Network allowlist.** The CC0 music sites (OpenGameArt, itch.io) were unreachable from both machines, so music had to be procedural. It works, but no one has listened to it yet.
2. **Syncing to the local folder.** The connected folder can't delete files, so `unzip -o` fails. The fix is a zip plus an overwrite-in-place script (`.sync/apply.py`), which leaves a leftover `.sync/` folder.
3. **Pushing the tag was blocked** by the proxy, while the branch push worked. `v0.1.0` exists only locally.
4. **Lost agent context.** The web agent couldn't be resumed after its transcript was lost, so small polish had to be done by the lead.
5. **Late features.** Audio, places, endings and records were all added mid-run. Each one took an extra agent round trip that the v0 spec could have avoided.
6. **The text writer was the bottleneck**, at about 45 minutes. Splitting writing by route (one agent per faction) would have finished sooner.

### Do differently next time
- Put audio, codex categories (including places), endings and records, and lore cards in the **v0 spec**.
- Create the **git repo at minute 0** and commit at each milestone. Keep the local folder a git clone, so syncing is just `git pull`.
- **Split writing across agents** by route when the content is large; keep one shared codex owner.
- Define **overlay layering** (toasts, modals, cards) in the spec.
- Add **human checkpoints**: a 10-minute playtest after the first route, and a listening pass on the music.
- Ask early which outputs need a real **human eye or ear** (art, music); automated checks can't judge taste.

### Reusable checklist
1. Pitch, scope, content budget (nodes, endings, assets)
2. Spec: schema, fixed asset key list, length limits, IP rules
3. Registry or API file that the lead owns
4. `CLAUDE.md` project memory, dev log, changelog
5. Folder ownership per role, then start agents in parallel
6. Placeholders and a tolerant boot, so it's playable early
7. Validator plus simulation, plus headless smoke tests with screenshots
8. Sync to the local folder or a git clone at each milestone
9. Human playtest, then polish, then tag and push

### 核心思路
- **设计文档就是合同。** 先定核心循环、胜负条件和范围，所有人照同一份文档开工。
- **内容是数据，不是代码。** 剧情节点、选项、效果、跳转写在数据文件里，引擎只读数据、执行规则。
- **游戏 = 一个状态对象 + 一个状态机。** 每个选择改变状态 → 结算效果 → 检查死亡 → 跳到下一个节点。
- **逻辑和显示分开。** 规则（`engine.js`）不碰页面，渲染和特效（`ui.js`）不决定规则。
- **资源流水线。** 美术由脚本生成，通过清单按代号引用；缺图时有退路。
- **存档 = 序列化的状态 + 版本号**，旧存档可以迁移，不会直接失效。
- **工具很值。** 链接检查加蒙特卡洛模拟跑局，是调平衡的办法。

### 做得好的
1. **规格先行。** 代理开工前先写好 `docs/SPEC.md`，整合时零冲突。它固定了节点格式和素材代号清单，所以写手可以先引用还没画出来的图。
2. **按文件夹分归属。** 每个角色负责整个文件夹（`data/`、`assets/`、`src/`），只有开发日志是共用的。没人覆盖过别人的文件。
3. **数据驱动 + 纯逻辑引擎。** `engine.js` 不碰页面，所以校验器能在 Node 里跑真实规则。每条路线模拟 3000 局，找出了光读文本发现不了的问题：
   - 一个从未触发的死亡结局
   - 平均流程偏短
   - 一个接近软锁的节点
4. **尽早可玩。** 缺图画成像素史莱姆，缺文件不影响启动，所以开工约 20 分钟就能玩，远早于内容写完。
5. **新需求做成可选字段。** 中途每个新需求都只在规格里加一个可选字段，旧数据照常可用，不用返工：
   - 卡片的展开说明（`more`）
   - 别名（`aliases`）
   - 死因（`ending.cause`）
   - 图鉴地点（`cat:"place"`）
6. **版权规则开局定好。** 官方角色只以 `omen_*` 意象场景图出现，不画肖像、不用标志。开局就定了，后面不用再讨论。
7. **截图当图片看。** 直接看截图和素材总览，发现了测试会放过的问题：
   - 提示框互相遮挡
   - 深色角色在暗场景里看不清
   - 文字被截断

### 踩过的坑
1. **网络白名单。** 两台机器都连不上 CC0 音乐站（OpenGameArt、itch.io），只好改成程序生成音乐。能用，但还没人听过。
2. **同步到本地文件夹。** 连接的文件夹不能删文件，所以 `unzip -o` 会失败。改用压缩包加原地覆盖脚本（`.sync/apply.py`），会留下一个 `.sync/` 目录。
3. **推送标签被代理拦截**，分支能推上去。`v0.1.0` 标签只在本地。
4. **代理上下文丢失。** 网页代理的记录丢了，无法继续，小的打磨只能由我自己做。
5. **功能加得晚。** 音频、地点、结局和生涯都是中途加的，每个都多了一轮和代理的来回，写进 v0 规格就能省掉。
6. **文本是瓶颈**，约 45 分钟。按路线拆成每个阵营一个代理会更快。

### 下次改进
- 把音频、图鉴分类（含地点）、结局和生涯、知识卡片写进 **v0 规格**。
- **一开始就建 git 仓库**，每个里程碑提交一次；本地文件夹直接是 git 克隆，同步就是 `git pull`。
- 内容量大时**按路线拆分文本代理**，图鉴保留一个统一负责人。
- 在规格里定义**弹层层级**（提示框、窗口、卡片）。
- 加**人工检查点**：第一条路线完成后试玩 10 分钟，音乐要有人试听一遍。
- 尽早确定哪些产出必须**真人看或听**（美术、音乐），自动检查判断不了好不好看、好不好听。

### 可复用清单
1. 定位、范围、内容预算（节点、结局、素材）
2. 规格：数据格式、固定素材代号、长度上限、版权规则
3. 由负责人维护的注册表或接口文件
4. `CLAUDE.md` 项目记忆、开发日志、更新日志
5. 按角色分文件夹归属，然后并行启动代理
6. 占位图加容错启动，尽早可玩
7. 校验器加模拟，加无头冒烟测试和截图
8. 每个里程碑同步到本地文件夹或 git 克隆
9. 真人试玩，然后打磨，然后打标签、推送
